## 初回と更新の扱いの整理（今は着手しない）

2026-09-28 に調べた結果、思ったより大きい。後から足した機能（`--new-hash` など）で、本番のパイプラインにゆがみが出ている。上の「許可待ちのまま次の実行が来ると、許可なしで公開される」も、ここに根がある。

### 1. 「新しい情報源」の決め方が 4 通りある（そのうち統一する）

| 場所 | 決め方 |
|---|---|
| `services/db_writer.py` の `_reconcile_records` | 登山道状況のレコードが 0 件（`disabled` を含む） |
| `management/commands/blog_sync.py` | ブログ記事の URL が 0 件（`disabled` を含む） |
| `views.py` の `recent_updated_sources` | 最新の同期が、情報源の作成から 1 日以内 |
| `services/fetcher.py` の `has_content_changed` | 前回のハッシュがない |

- どれも「この情報源は新しいか」を問うているが、見ているものが違う。1 か所だけ直すと、ほかとずれる。
- 案：情報源（`DataSource`）に「確認済み」の印（例：オーナーが管理画面で最初に許可した日時）を持たせ、`db_writer` と `blog_sync` は「未確認の情報源なら `disabled=True` で作る」だけにする。レコードの件数を数えなくなるため、上の許可待ちの不具合も根から消える。`views.py` の「作成から 1 日以内」も置き換えられる可能性がある。マイグレーションが必要。

### 2. `--new-hash` の判定が 2 か所にあり、片方は通らない

- `services/pipeline.py`：`new_hash_mode` なら、ハッシュが同じでも先に進み、必ず `content_changed=True` で返す。
- `management/commands/trail_sync.py` の `process_result`：`not content_changed` の中で `new_hash_mode` を見て分岐しているが、上のとおり `content_changed=False` と `new_hash_mode` が同時に来ることはない。`else`（「NEW-HASHモード: 既存データと再度照合します」）は動かない。
- 経緯：`--new-hash` は #25（2026-01-14、`02bf47c`）で追加した。追加したときの `pipeline.py` の条件は `if new_hash:`（ハッシュの文字列で、常に真）で、のちに `self.new_hash_mode` に直っている。`trail_sync.py` 側の分岐が何のために必要だったかは、整理するときに当時の差分で確かめる。

### 3. `fetcher.py` の `not previous_hash` は判定には不要

- `has_changed = not previous_hash or current_hash != previous_hash` は、`previous_hash` が `None` / `""` でも後半だけで `True` になる。前半は、ログの文を「初回」と「変更」で分けるためだけに使われている。害はない。

## 見送ったもの

### httpx から httpx2 への移行
- httpx2 は PyPI の別パッケージ（2.13.1、https://github.com/pydantic/httpx2 、「The next generation HTTP client.」）。
- 影響箇所：`fetcher.py`、`pipeline.py`、`blog_fetcher.py`、`slack_notifier.py`、`fetch_url.py`、`blog_sync.py`、`tests/trail_status/conftest.py`（`mock_async_client`）、`test_fetcher.py` など。
- google-genai / openai / langsmith が httpx に依存しているため、直接の依存だけを置き換えると httpx と httpx2 の両方が入る。API の違いをまとめた一次情報も見つからなかった。
- httpx と httpx2 は互換ではない。httpx2 が入っているとそちらを優先して使うライブラリがあるため、依存経由で httpx2 が入るだけで挙動が変わりうる。
- openai 3 系（3.19.2）は httpx2 を必須の依存にしている。`uv.lock` の openai が 2.44.0 なのは、`uv lock` が既存のバージョンを自動では上げないため（`pyproject.toml` に上限はなく、`uv lock --dry-run --upgrade-package openai` では衝突なく 3.19.2 に上がる）。
- openai 3 系に上げると `httpx2` / `httpcore2` / `httpx2-jsfetch` / `truststore` が追加される。`truststore` は OS の証明書ストアを使うため、HTTPS の挙動に注意する。
- 2026-09-27 時点で、google-genai（2.10.0）と langsmith（0.9.3）は httpx2 を参照していない。このリポジトリのコードも SDK に httpx のクライアントを渡しておらず、SDK の呼び出しで httpx の例外を捕まえていない。
- 再検討するときは、openai 3 系への更新と、その時点の google-genai / langsmith が httpx2 を優先するかの確認から始める。

## 依存パッケージの更新

2026-09-27 時点で `uv lock --dry-run --upgrade` を実行すると、更新 76・追加 7・削除 2。

- メジャーバージョンが上がるもの：openai（2.44.0 → 3.19.2）、cryptography（49 → 50）、xxhash（3 → 4）、sudachidict-core（20260428 → 20260723.1）。
- 差が大きい直接の依存：langsmith（0.9.3 → 0.14.1）、google-genai（2.10.0 → 2.25.0）、sudachipy（0.6.11 → 0.7.0）、django（6.0.6 → 6.1.1）、ruff（0.15 → 0.16）。
- langsmith 0.14.1 は httpx2 を必須にしている。openai 3 系も同じ。google-genai 2.25.0 は httpx のまま。全体を更新すると httpx と httpx2 の両方が入る。
- sudachipy / sudachidict の更新は形態素解析の結果を変えうるため、名寄せの結果に影響する可能性がある。
- ruff の更新で lint の結果が変わる可能性がある。

一度にすべてを上げず、次の単位に分ける。
1. パッチ・マイナーの更新（django、gunicorn など）
2. openai 3 系と langsmith 0.14 系（httpx2 を使う組）。ステージングで LLM の呼び出しを確認する
3. sudachipy と sudachidict。`test_matching` コマンドで更新前後の照合結果を比べる

更新には `uv lock --upgrade-package <名前>` を使う。`uv lock` は既存のバージョンを自動では上げない。同期は `uv sync --all-extras --all-groups` で行う。
